The reporting problem

A failed reporting run should not leave users with a broken latest report or hide the reason it failed. Purchase-order and master-data checks must happen before publication.

Approach

  1. Validated order keys, dates, quantities, supplier/item references and bill-of-materials relationships, including cycle detection.
  2. Produced accepted-record CSVs, diagnostic CSVs, JSON summaries and readable HTML reports. Content-based run IDs make repeated inputs reproducible.
  3. Separated diagnostic output from promotion of the latest-success pointer, so a failed run retains its evidence without replacing the trusted report.

FINDING → NEXT ACTION

The clean fixture accepts 1,500 records with no issues. The deliberately dirty fixture contains 1,501 input rows, accepts 1,496, rejects five and reports nine issues. These are controlled failure tests, not live operational incidents.

Resolve exceptions at the source and rerun validation before promotion. The pipeline identifies and quarantines problems; it does not silently repair records.

Verification

Twelve unit tests cover clean/dirty fixtures, date boundaries, partial receipts, invalid references, BOM cycles and publication protection. Both generated HTML reports and the Python source are available to inspect.

Scope and limitations

A local Python implementation, not a deployed service. Power Automate delivery is a proposed workflow only. No scheduler, email integration, live ERP connection or measured time-saving claim.
